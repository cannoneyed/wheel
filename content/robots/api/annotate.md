## `AnnotateSink`

Kind: interface. Source: [packages/wheel/src/annotate/types.ts:229](../../../packages/wheel/src/annotate/types.ts#L229).

Where notes are sent, and read back from. One URL, two methods, and that is the whole contract: - `POST <url>` — save one note. The body is `{ id, payload, markdown, png?, video?, audio? }`, where `payload` is a {@link NotePayload} and the media are `data:` URLs. Answer `{ ok: true, command?, location? }` — `command` is something pasteable (the dev server returns `read <path>/note.md`), `location` a URL where the note now lives. A non-ok answer, or none, makes the page fall back to downloading the note as one file. `id` is the note's identity, not the request's: the page re-POSTs the same id when someone rewrites a note, and a sink must REPLACE that note rather than store a second one. A rewrite sends no media — what was captured is not re-captured — so keep the attachments already held under that id. - `GET <url>` — the saved notes as `{ ok: true, notes: [{ id, payload }] }`, newest first. Nothing on the page needs the list; it is the capability probe, and answering at all is what tells the page saving is possible here rather than downloading. The default is the dev server's `/__wheel/note`, which writes a directory per note. Point it somewhere else — a Durable Object, an issue tracker, a bucket — and nothing else about the annotator changes.

## `NoteAnchor`

Kind: interface. Source: [packages/wheel/src/annotate/types.ts:48](../../../packages/wheel/src/annotate/types.ts#L48).

What a note is about: the rectangle that was drawn, and what was under it. There is one anchor shape because there is one interaction — drawing the box IS picking the target. What was underneath is described BOTH ways, because the page may be a wheel app or may be plain prose: - as a component (`instanceId`, `name`, `ancestors`), for an app; - as plain DOM (`domPath`, `element`, `text`), for a docs paragraph or a landing headline, where there is no component to name but there is very much something on the screen. Either half may be empty. Both are recorded whenever they exist, because the agent reading the note later takes whichever the page actually had.

## `Recorder`

Kind: class. Source: [packages/wheel/src/annotate/recorder.ts:176](../../../packages/wheel/src/annotate/recorder.ts#L176).

The event buffer plus its taps. One per app; `AnnotateService` owns it. It runs only while someone is recording. An earlier design kept a rolling 60-second buffer alive for the whole session, so a note could carry the minute BEFORE the box was drawn — appealing, but it meant every session paid for taps it would probably never use, and what it mostly caught was the act of using the tools. `install()` / `uninstall()` are the only things that touch global state, and both are idempotent.

## `renderNoteFile`

Kind: function. Source: [packages/wheel/src/annotate/note-format.ts:233](../../../packages/wheel/src/annotate/note-format.ts#L233).

The whole note as ONE self-contained markdown file, for when there is no dev server to write a directory — a production page, a static preview. Everything that would have been separate files is folded in: the screenshot as an inline data URL, and the complete payload as a fenced JSON block so nothing is lost on the way. Audio and video are deliberately left out; they are megabytes of base64 that no reader of a markdown file wants, and the transcript — the part an agent can actually use — is already in the prose.
