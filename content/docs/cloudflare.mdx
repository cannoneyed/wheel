# Cloudflare deployment

Wheel deploys the `main` website artifact to `wheel.dev`. Other branches use isolated website previews. Every branch uses an isolated tracker preview.

```text
main push                       other branch push
    |                                  |
    v                                  v
wheel-site -> wheel.dev        wheel-site-<branch-key>.workers.dev
    |
    +-------------------------- wheel-tracker-<branch-key>.workers.dev
```

The website Worker serves static assets. It has separate fallbacks for `/`, `/docs/*`, and `/demos/*`.

The tracker Worker serves Axle assets. It sends `/sync/*` and `/readyz` to one Durable Object named `axle-demo`. The object owns migrations, deterministic demo data, the Wheel server, SQLite storage, and rollover alarms.

The production scope contains the static website only. Tracker identity and data remain branch-local previews.

## WebSocket lifecycle

Tracker uses the Durable Object WebSocket Hibernation API. The upgrade path calls `ctx.acceptWebSocket(server)`. It does not call `server.accept()`.

One socket carries all sync operations in both directions:

| Client message | Server result |
| --- | --- |
| `subscribe` | Full snapshot, then delta events |
| `unsubscribe` | Subscription release |
| `mutate` | Mutation result and peer deltas |
| `presence` | Presence events to peer sockets |

Before the object sleeps, Wheel stores the authenticated principal, presence state, subscription names, parameters, and IDs in the socket attachment. Wheel limits its JSON state to 15 KiB. Cloudflare limits the serialized attachment to 16 KiB.

When a message wakes the object, its constructor runs again. Boot applies migrations, creates the engine, reads every socket from `ctx.getWebSockets()`, and restores each subscription. Every query runs once to rebuild its comparison baseline. The waking message runs only after restore completes.

Hibernation does not make the browser reconnect. Subscription IDs and presence stay unchanged.

A deployment is different. Cloudflare terminates WebSockets when Durable Object code changes. The browser reconnects and requests fresh snapshots. The new connection clears old peer presence before the server sends its current peers. The client outbox remains in IndexedDB and replays unconfirmed mutations by mutation ID.

## Schema and deploy versions

Wheel uses three version values. Do not combine them.

| Version | Owner | Change it when |
| --- | --- | --- |
| Sync protocol | Wheel | A frame shape is no longer readable by the other version |
| Application version | App | Client and server behavior can become incompatible |
| SQLite schema version | Migration list | A migration is appended |

The WebSocket handshake sends the protocol and application versions. The server returns its application and SQLite schema versions.

During a rolling deployment:

1. A new client can reach an old Durable Object. The server returns `server_updating`. The client retries without reloading.
2. An old client can reach a new Durable Object. Keep `minimumClientVersion` at the old version while it remains compatible.
3. For a breaking change, raise `minimumClientVersion`. The server returns `client_outdated`. The app reloads its assets.
4. A protocol mismatch also reloads the app.

Put application versions in one shared file. Tracker uses `packages/tracker/sync-version.ts` from the browser, Bun server, and Cloudflare Worker.

Include the application version in the IndexedDB snapshot scope. Keep the outbox scope stable. A row-shape change then deletes old snapshots without losing pending edits.

## Migration rules

`applyDurableObjectMigrations()` runs inside `ctx.blockConcurrencyWhile()` before engine boot.

```ts
// Intentionally condensed: migration result becomes the WebSocket hello schema version.
const migration = await applyDurableObjectMigrations(
  storage,
  TRACKER_MIGRATIONS
);

const sockets = new SyncSocketServer({
  server,
  applicationVersion: TRACKER_APPLICATION_VERSION,
  minimumClientVersion: TRACKER_MINIMUM_CLIENT_VERSION,
  schemaVersion: migration.toVersion
});
```

The default table is `_wheel_schema_migrations`. Do not reuse an application migration table with a different column format.

Use these rules:

1. Start at version 1. Keep versions contiguous.
2. Append migrations. Never rename or edit a migration that ran anywhere. Wheel stores and checks a SHA-256 SQL checksum.
3. Put all pending migrations in one storage transaction.
4. Do not use `PRAGMA user_version`; Durable Object SQLite does not support it.
5. If storage is newer than the running code, fail boot with `schema_too_new`.

There are no down migrations. Roll forward with a new migration. A code rollback can run only if it understands the current schema version.

`cloudflare/tracker.worker.test.ts` proves all required paths on real Durable Object test storage. It checks hibernation resume, stable subscription IDs, presence restore, deploy closure, stale socket schema refusal, version mismatches, migration idempotence, changed names or SQL, newer storage, and transaction rollback.

## Run the local proof

Use Bun 1.3.14 and Node 20.19 or later. The repository runs Wrangler through Bun.

```sh
bun install --frozen-lockfile
bun run check:cloudflare
bun run website:build
bun run --cwd packages/tracker build
bun node_modules/wrangler/bin/wrangler.js deploy --dry-run --config wrangler.website.jsonc
bun node_modules/wrangler/bin/wrangler.js deploy --dry-run --config wrangler.tracker.jsonc
```

`bun run check` remains the serial local gate. Buildkite runs its check lanes in parallel.

## Configure Cloudflare

1. Open **Workers & Pages** in the deployment account.
2. Configure the account's `workers.dev` subdomain if Cloudflare asks for one.
3. Copy the account ID from the dashboard URL or account overview.
4. Open **My Profile > API Tokens**, then select **Create Token**.
5. Start with **Edit Cloudflare Workers** and limit **Account Resources** to the deployment account.

Save the generated token when Cloudflare shows it. Cloudflare does not show the token value again.

> **Security:** Do not create Workers, Durable Objects, or routes by hand. The first trusted deploy creates them.

Cloudflare documents the [token flow](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/), [token template](https://developers.cloudflare.com/fundamentals/api/reference/template/), and [`workers.dev` setup](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/).

## Create the Buildkite agent

1. Open **Agents**, then select the cluster that will own this pipeline.
2. Select **New Queue** and use the exact key `hosted-linux`.
3. Select hosted Linux, AMD64, and medium capacity.
4. Open **Agent Images**, then create an image for the queue.
5. Add the image content below after Buildkite's fixed `FROM` line.

```dockerfile
ARG NODE_VERSION=20.19.5
ENV BUN_INSTALL=/opt/bun
ENV PLAYWRIGHT_BROWSERS_PATH=/opt/ms-playwright
ENV PATH="/opt/bun/bin:${PATH}"

RUN apt-get update \
  && apt-get install -y --no-install-recommends bash ca-certificates curl git unzip xz-utils \
  && rm -rf /var/lib/apt/lists/*
RUN curl -fsSL "https://nodejs.org/dist/v${NODE_VERSION}/node-v${NODE_VERSION}-linux-x64.tar.xz" \
  | tar -xJ -C /usr/local --strip-components=1
RUN curl -fsSL https://bun.com/install | bash -s "bun-v1.3.14"
RUN npx -y playwright@1.61.1 install --with-deps chromium
RUN node --version && bun --version
```

Select the queue, open **Base image**, and make this agent image the queue default. Create a new image when the locked Playwright version changes.

Buildkite adds `buildkite-agent` and Docker to hosted Linux images. The image supplies Git, Node, Bun, Chromium, and Chromium's system libraries. See [hosted queues](https://buildkite.com/docs/agent/queues/managing) and [custom agent images](https://buildkite.com/docs/agent/buildkite-hosted/linux/custom-agent-images).

## Create the Buildkite secrets

Open **Agents > cluster > Secrets**. Create these secrets in the same cluster as `hosted-linux`:

| Key | Value |
| --- | --- |
| `CF_WORKERS_TOKEN` | The Cloudflare API token |
| `CF_ACCOUNT_ID` | The 32-character Cloudflare account ID |

The pipeline maps these keys to `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Only deploy and cleanup jobs receive them.

Buildkite explains this cluster-scoped flow in [Buildkite secrets](https://buildkite.com/docs/pipelines/security/secrets/buildkite-secrets). Wrangler documents both [Cloudflare environment variables](https://developers.cloudflare.com/workers/wrangler/system-environment-variables/).

## Create the Buildkite pipeline

1. Connect the full-access Buildkite GitHub App to this repository.
2. Select **Pipelines > New pipeline** and choose the cluster that contains `hosted-linux`.
3. Select this repository and use HTTPS checkout.
4. Put the upload step below in Buildkite's YAML steps editor.
5. Create the pipeline, then open **Settings**.

```yaml
steps:
  - label: ":pipeline: Upload"
    agents:
      queue: "hosted-linux"
    command: "buildkite-agent pipeline upload"
```

The upload command reads `.buildkite/pipeline.yml` from the checked-out commit. Buildkite documents this in [pipeline upload](https://buildkite.com/docs/agent/cli/reference/pipeline).

Set the GitHub options as follows:

| Setting | Value |
| --- | --- |
| Build branches | Enabled |
| Branch filter | Empty |
| Build pull requests | Enabled |
| Skip pull requests with an existing commit build | Enabled |
| Publish commit status | Enabled |
| Publish commit status for each step | Disabled |
| Build tags | Disabled |

Open **Settings > Builds**. Enable **Skip Intermediate Builds** and **Cancel Intermediate Builds** with empty filters.

The deploy condition accepts trusted branch-push webhooks only. Pull requests run checks without Cloudflare secrets. Fork pull requests cannot deploy.

Buildkite documents the [GitHub App](https://buildkite.com/docs/pipelines/source-control/github), [queued-build skipping](https://buildkite.com/docs/pipelines/configure/skipping), and [running-build cancellation](https://buildkite.com/docs/pipelines/configure/canceling-builds).

## Protect `main`

GitHub hosts the repository and enforces one required status. Buildkite runs all CI jobs and publishes `buildkite/wheel` after the complete build finishes.

1. Open **Settings > Branches**, then add a branch protection rule for `main`.
2. Enable **Require a pull request before merging**.
3. Enable **Require status checks to pass before merging** and **Require branches to be up to date before merging**.
4. Add `buildkite/wheel` as the only required status check.
5. Enable **Do not allow bypassing the above settings**.

There are no files in `.github/workflows`. GitHub Actions does not run CI for this repository.

## Configure all CI modes

The standard mode needs no variable. It runs static, unit, browser, and Workers checks. It then builds both applications in parallel.

Create these extra Buildkite modes:

| Mode | `WHEEL_CI_MODE` | Start |
| --- | --- | --- |
| Standard | Omit | GitHub branch or pull request webhook |
| Nightly fuzz | `fuzz` | `0 3 * * * America/New_York` |
| Branch cleanup | `cleanup` | `0 4 * * * America/New_York` |

Open **Settings > Schedules** to create the fuzz and cleanup schedules. Use the default branch and put `WHEEL_CI_MODE` in each schedule's environment.

Run one successful standard build and one fuzz build after you change either schedule.

Buildkite schedules accept a branch, commit, and environment. See [scheduled builds](https://buildkite.com/docs/pipelines/configure/workflows/scheduled-builds).

## Run the first deployment

1. Push a commit to a branch in this repository.
2. Open the Buildkite build and wait for all check lanes.
3. Confirm both build jobs pass their Wrangler dry runs.
4. Open the **Wheel production deployment** or **Wheel branch preview** annotation after deploy finishes.
5. Open both URLs and the tracker `/readyz` URL.

A manual standard build tests the pipeline but does not deploy. The deploy condition requires a GitHub branch-push webhook.

## Branch deploy behavior

`scripts/ci/branch-key.ts` makes one stable key from the complete branch name. The readable part is 30 characters. An eight-character SHA-256 suffix prevents slash and dash variants from colliding.

The deploy step downloads the exact website and tracker assets from the build steps. It deploys both Workers in parallel. It then checks the website URL, tracker URL, and tracker `/readyz` route. A Buildkite annotation contains both checked URLs and the commit.

`main` reuses the stable website Worker `wheel-site`. Other branches reuse names derived from their branch keys. Tracker Durable Object data stays in place while its branch exists.

## Cleanup behavior

`scripts/ci/cleanup-branches.ts` reads live Git branch refs and Cloudflare Worker tags. It manages only `wheel-site-*` and `wheel-tracker-*` names. It does not manage the production Worker `wheel-site`.

The first cleanup after branch deletion adds an `orphaned-at:<timestamp>` tag. A restored branch clears this tag. Cleanup deletes both Workers after the tag is seven days old.

Cleanup is a dry run unless it receives `--apply`. Deletion also removes branch tracker data.

## Production website

`wrangler.website.production.jsonc` owns the `wheel.dev/*` Worker route. `scripts/ci/deploy-branch.ts` selects this configuration only when `BUILDKITE_BRANCH` is `main`.

Wrangler injects `BUILDKITE_COMMIT` as `DEPLOY_COMMIT`. The Worker returns it in `x-wheel-commit`, and the deploy job rejects a successful response from any older origin.

Do not add `tracker.wheel.dev` to this configuration. Production tracker work must define identity, workspace provisioning, authorization, backup, and restore first.
