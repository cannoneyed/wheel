# Server handlers in depth

On top of a backend you write four things: your schema and migrations, the two handler shapes, the four id rules that bit this repo, and the SQLite dialect details that show up in every binding. [Server](#/server) picks the backend itself.

## Schema and migrations

Wheel generates no application schema. It owns its own bookkeeping tables and nothing else — your tables, your DDL, your migration runner. There is no `wheel migrate` command.

Copy the pattern in `packages/tracker/server/schema.ts`: a literal array of versioned migrations, a table recording which ones ran, and one `begin immediate` transaction around the whole apply:

<CodeExample example={migrationsSource} />

Three properties make this worth copying:

1. **Append, never edit.** Version 1 is frozen the moment it runs anywhere. A schema change is a new entry.
2. **One transaction.** `begin immediate` takes the write lock up front, so a crash mid-migration rolls back to a clean version rather than a half-applied one.
3. **Production never depends on seed DDL.** Tests and the dev server run the same `migrations` array the production boot runs; seed rows are a separate, dev-only step.

The DDL itself lives next to the bindings that use it — each `*.server.ts` exports its own `*_DDL` array, and `schema.ts` concatenates them.

## The handler contract

A query binding answers two questions: *what are this query's rows right now*, and *when might that answer have changed*. Everything else — diffing, `seq`, whole-row deltas, schema validation — stays with the engine.

`serveQuery({ query, sql })` is sugar. It desugars to `SqlQueryHandler`, which is useful when you want the third option, `prune`:

```ts
// Excerpt: activityByIssue and Activity come from the matching .sync.ts module.
export const activityByIssueServer = serveQuery({
  query: activityByIssue,
  handler: SqlQueryHandler<{ issueId: string }, Activity>({
    sql: (params) => sql`select id, issue_id as "issueId", detail from activity
                         where issue_id = ${params.issueId} order by created_at desc limit 50`,
    prune: (image, params) => (image.n?.issue_id ?? image.o?.issue_id) === params.issueId
  })
});
```

The query's default `dependsOn: ['activity']` is coarse: *any* write to `activity` re-runs *every* open activity query. `prune` narrows that. It receives one touched row's before/after images — `image.o` and `image.n`, raw table shape with snake_case columns, not the query's projected row — and returns whether that write could possibly matter to this subscription. Return `false` for every touched row and the re-run is skipped entirely.

<Aside kind="warning">
  <strong><code>prune</code> is an optimization, never authorization.</strong> It requires
  row-image data from the backend. The current SQLite backends do not capture row images, so
  they always re-run the query. When images are missing, the engine stays correct and skips no
  work. A
  <code>prune</code> that filters by user does not keep anyone's rows private. The
  <code>sql</code> does that, by comparing <code>params</code> against the connection's
  <code>principal</code>.
</Aside>

When SQL alone can't answer, drop to a hand-built `QueryHandler`. The tracker's full-text search is the reference (`packages/tracker/src/sync/search.server.ts`): FTS5 tables kept fresh by triggers, ranked by `bm25`, invalidated by *both* declared dependencies and a push channel:

```ts
// Intentionally condensed: search.server.ts builds a safer FTS5 match expression than this.
export const searchHandler: QueryHandler<{ q: string }, SearchResult> = {
  kind: 'tracker-search',
  subscribe(_params, invalidate) {
    searchInvalidation.listeners.add(invalidate);
    return () => searchInvalidation.listeners.delete(invalidate);
  },
  async run(params, ctx: QueryHandlerCtx) {
    return (await ctx.query('select ... where issue_fts match ?', [toMatchExpr(params.q)])) as SearchResult[];
  }
};
```

`ctx.query(text, params)` is read-only database access; `ctx.principal` is the identity authenticated when this subscription's connection opened. `subscribe(params, invalidate)` returns its own unsubscribe — call `invalidate()` whenever the answer *may* have changed and the engine coalesces one re-run plus diff onto its writer loop. A no-op change emits nothing, so over-notifying is cheap. An external index — Meilisearch, a materialized view, a webhook feed — plugs in here. The query needs a non-empty `dependsOn` list or a handler `subscribe`; `serveQuery` throws at declaration time otherwise.

Mutation handlers reject with `rejection(code, message)` from `wheel/sync` — a typed refusal the client surfaces as `info.rejection`, distinct from a crash. Pull repeated business rules into a guard helper and call it first:

```ts
// Excerpt: the shared guard from packages/tracker/src/sync/issues.server.ts.
async function requireActive(tx: ServerTx, issueId: string): Promise<void> {
  const [row] = await tx.sql<{ archivedAt: number | null }>`
    select archived_at as "archivedAt" from issues where id = ${issueId}`;
  if (!row) throw rejection('missing', 'This issue no longer exists.');
  if (row.archivedAt !== null) throw rejection('archived', 'This issue is archived — unarchive it first.');
}
```

Every handler that edits an issue opens with `await requireActive(tx, args.issueId)`. One guard, one message, one code, checked in the transaction that does the write.

## The four id rules

These are the footguns. Each one produced a real bug in this repo.

**1. Both sides must mint the same ids, in the same order, on every branch.** The client pre-generates a deterministic id stream for a mutation; the server replays that same stream. If the optimistic handler takes a branch that mints one id and the server takes a branch that mints zero, the streams desynchronize and the mutation fails.

The bug:

```ts
// Intentionally wrong: one branch mints an id, the other doesn't — the streams desynchronize.
const existing = cache.list(cells).find((cell) => cell.row === args.row && cell.col === args.col);
if (existing) {
  cache.update(cells, existing.id, { value: args.value });
} else {
  cache.put(cells, { id: ctx.newId('cell'), row: args.row, col: args.col, value: args.value });
}
```

The fix:

```ts
// Excerpt: the fix, from sheet.sync.ts and sheet.server.ts — both mint first, unconditionally.
// "Always mint first — mirrors sheet.server.ts exactly."
const id = ctx.newId('cell');
if (args.value === '') { /* delete path — id unused, but the stream stays aligned */ }
```

Mint every id up front, before any branch, even on paths that will not use it.

**2. A creating mutation carries its new id in `args`.** `invert` runs *before* the optimistic apply, so an inverse like "archive that issue" can only name its target if the id already travels in the args. The caller mints it with `client.newId(prefix)` and passes it in.

The bug:

```ts
// Intentionally wrong: the id is minted inside the handler, so invert has nothing to name.
optimistic: (cache, args, ctx) => cache.put(issues, { id: ctx.newId('issue'), ...args })
```

The fix:

```ts
// Excerpt: from IssueService.create — the id is minted by the caller and returned to it.
const issueId = this.client.newId('issue');
this.watch(this.mutate(issueCreate, { issueId, teamId, ...draft }), 'create the issue');
return issueId;
```

**3. Server-authored rows never call `ctx.newId`.** A row the client does not know exists — an activity entry, a notification — has no id in the client's stream, so asking for one throws `id_stream_exhausted`. Derive the id from data the replay will reproduce identically: `(mutationId, entityId, kind)`.

The bug:

```ts
// Intentionally wrong: the client never minted an id for a row it doesn't know about.
const id = ctx.newId('activity');
```

The fix:

```ts
// Excerpt: from logActivity — deterministic id plus an idempotent upsert.
const id = `activity_${ctx.mutationId.slice(2)}:${issueId.slice(-8)}:${kind}`;
await tx.sql`insert into activity (id, issue_id, kind, created_at)
             values (${id}, ${issueId}, ${kind}, ${ctx.now()})
             on conflict (id) do nothing`;
```

An exactly-once replay of the mutation regenerates the same id, so `on conflict do nothing` makes the second run a no-op.

**4. Server-assigned fields get an optimistic sentinel.** A per-team sequence number, a server clock, a database default — anything only the server can assign race-free — cannot be guessed by the optimistic handler. Write a sentinel the UI knows how to render as pending, and let the rebase swap in the real value on confirmation.

The bug:

```ts
// Intentionally wrong: the client guesses the next number and every concurrent create collides.
cache.put(issues, { ...args, number: highestNumberInCache + 1 });
```

The fix:

```ts
// Excerpt: issues.sync.ts writes the sentinel; issues.server.ts assigns the real value.
cache.put(issues, { ...args, number: 0 }); // 0 = pending; UI renders "ENG-…"
// server: select coalesce(max(number), 0) + 1 as next from issues where team_id = …
```

## SQLite dialect notes

The reference apps target SQLite. Three details show up in nearly every binding:

- **Booleans are `integer`.** SQLite has no boolean type. Declare the column `integer not null default 0`; the backend coerces 0/1 back to real booleans as it reads rows, so schema validation still sees booleans. `coerceParams` turns a bound `true`/`false` into 1/0 on the way in — `better-sqlite3` throws on a raw boolean bind.
- **Fractional positions are `real`.** Ordering keys sit between their neighbours rather than renumbering the list, so the column must hold fractions: `position real not null default 0` (`packages/demos/src/todos/sync/todos.server.ts`).
- **Quote reserved words.** `row` is one. `packages/demos/src/sheet/sync/sheet.server.ts` writes `"row"` everywhere, including in `on conflict ("row", col)`.

<Aside kind="note">
  Placeholders are bound positionally, once per occurrence. The rewriter maps each
  <code>$n</code> to a <code>?</code> and does <strong>not</strong> reuse a parameter across
  positions — so a value needed twice is passed twice, as
  <code>[match, match]</code> in the search handler above.
</Aside>
