# Production

Wheel's production shape is a static browser build plus a Cloudflare Worker and Durable Object. The browser opens one WebSocket at `/sync/websocket`. The Durable Object owns one workspace, one SQLite database, and every socket for that workspace.

```text
browser assets on a CDN
          |
          | /sync/websocket
          v
Cloudflare Worker -- workspace id --> Durable Object
                                      SQLite + SyncServer
```

The outer Worker authenticates the upgrade and chooses a Durable Object from trusted identity. The object applies migrations before engine boot, accepts the socket with the Hibernation API, and restores its attachment after wake. Keep browser assets separate from the sync Worker when that makes static hosting simpler; the browser only needs the correct WebSocket origin.

## Durable Object entry point

`cloudflare/tracker-worker.ts` is the reference. Its preview routes `/sync/*` and `/readyz` to one object named `axle-demo`. A multi-workspace deployment derives the object name from the authenticated workspace instead.

Boot the object in this order:

1. Run `applyDurableObjectMigrations()` inside `ctx.blockConcurrencyWhile()`.
2. Build `createCloudflareSyncBackend()` from `ctx.storage`.
3. Create the sync engine and `SyncSocketServer`.
4. Restore every socket returned by `ctx.getWebSockets()`.
5. Process new WebSocket messages only after restore completes.

Accept sockets with `ctx.acceptWebSocket(server)`, not `server.accept()`. Wheel stores the principal, presence, subscriptions, rate state, and version data in the socket attachment. Keep that JSON below Wheel's 15 KiB limit and Cloudflare's 16 KiB attachment limit.

Use `applicationVersion` for client/server behavior and the migration result for `schemaVersion`. Keep the IndexedDB snapshot scope versioned, but keep the outbox scope stable. A deploy may close sockets; the browser reconnects, fetches fresh snapshots, and replays unconfirmed mutation IDs.

## Worker bindings and secrets

Cloudflare passes bindings and secrets through the Worker's `env` argument. Declare the Durable Object namespace in Wrangler configuration. Store session verifier keys, signing keys, and service credentials as secrets. Do not put them in Vite variables or `wheel/config`.

Fail a request when identity cannot select exactly one allowed workspace. Do not accept workspace, actor, or session claims from a sync message. Those values come from the authenticated upgrade and remain attached to the socket.

Expose `/readyz` through the same object route used by sync. Readiness should prove that the object can boot, migrate, and query storage. Cloudflare manages process liveness.

## WebSocket limits and errors

Set `maxMessageBytes` and `messagesPerMinute` on `SyncSocketServer`. Limits apply per connection and survive hibernation because their state lives in the attachment. One noisy tab does not throttle other tabs behind the same network address.

Keep `detailedErrors` off in production. The server then returns stable error codes without exposing internal messages. Application logs still receive the full error.

Cloudflare can close sockets during a code deploy. It also enforces platform limits on message size, CPU, storage, alarms, and object concurrency. Treat those limits as part of the runtime contract; do not translate them into process or HTTP-body settings.

## Self-hosted Bun

`packages/tracker/server.ts` is the local and self-hosted alternative. It uses the same sync declarations and WebSocket protocol with an in-process SQLite database.

A self-hosted process must provide `/healthz` and `/readyz`, persistent storage, verified authentication, per-socket limits, sanitized errors, and graceful shutdown. Read `process.env` once, validate it, and refuse production defaults such as `:memory:` storage or demo authentication. Honor `PORT` when a supervisor assigns it.

Memoize shutdown so repeated `SIGTERM` or `SIGINT` signals wait on one close. Stop accepting sockets, close them, stop the Bun server, and await `syncServer.close()`. The sync server owns its backend, so do not close the SQLite driver a second time.

<Aside kind="note">
  <strong>Server config and browser config are different systems.</strong> Cloudflare uses Worker
  bindings and secrets. Bun uses <code>process.env</code>. The browser uses
  <code>wheel/config</code>, and secrets must never cross into it. See{' '}
  <a href="#/configuration">Configuration</a>.
</Aside>

## Deploying under a base path

Serving the app at `/app/` instead of `/` takes two coordinated changes.

1. Build with the prefix: `base: '/app/'` in `vite.config.ts` (the demos read it from an env var so one config serves both shapes).
2. Override the router's history so it strips that prefix:

```tsx
// Excerpt: main.tsx — the router follows the build's base path.
import { basedHistoryOverride } from 'wheel/router';

const base = import.meta.env.BASE_URL; // '/' or '/app/'
render(() => (
  <ServiceProvider overrides={base === '/' ? [] : [basedHistoryOverride(base)]}>
    <appRouter.Root />
  </ServiceProvider>
), document.getElementById('root')!);
```

`basedHistory` wraps the real browser history: routes still match `/settings`, the address bar shows `/app/settings`, and `<Link>` writes the prefixed href. Skip the override when the base is `/` (it returns the inner history unchanged anyway).

The host needs one more rule: **every unmatched path under the base must serve `index.html`**. Path routing means `/app/issues/abc` is a real URL a user can reload or paste, and without the fallback the host 404s a file that was never emitted. `vite preview` applies this rule, which is why the browser suites run against it; on Netlify, Vercel, Caddy, or nginx it is one rewrite line.

## The no-hosted-backend option

Wheel can also run its real server engine on WASM SQLite inside a SharedWorker. The sync protocol uses `postMessage`. One engine per origin lets tabs sync with each other and share presence.

Two interfaces make this a proxy rather than a port: `SqliteDriver` (three synchronous calls) and `SyncTransport` (six async methods). Build it with `VITE_SYNC_MODE=browser vite build`. This is how a static site hosts fully live demos.

Databases are `:memory:` and die with the last tab, so this shape suits demos, offline sandboxes, and single-visitor tools. It does not provide shared production data. Read `packages/demos/src/shared/in-browser/README.md` for the design and its planned OPFS persistence.

## Observability

Wheel logs through one door: `logger` from `wheel/core`. Install a sink and every `logger.warn` and `logger.error` in your app and in the framework passes through your function on its way to the console:

```ts
// Excerpt: main.tsx — route warnings and errors to your backend and the console.
import { setLoggerSink } from 'wheel/core';

setLoggerSink((level, parts) => {
  if (level === 'warn' || level === 'error') {
    void fetch('/telemetry', { method: 'POST', body: JSON.stringify({ level }) });
  }
  console[level](...parts);
});
```

Your sink owns the console call. Forget it and the logs stop printing.

For uncaught exceptions and rejected promises too, use the capture buffer instead. `startErrorCapture()` is idempotent, installs the window handlers *and* the logger sink itself, and returns a 100-entry ring buffer you can subscribe to:

```ts
// Excerpt: main.tsx — one buffer for throws, rejections, and logger calls.
import { startErrorCapture, formatEntry } from 'wheel/debug';

const log = startErrorCapture();
log.subscribe(() => {
  const latest = log.entries().at(-1);
  if (latest?.level === 'error') void fetch('/telemetry', { method: 'POST', body: formatEntry(latest) });
});
```

`formatEntry` renders one entry as a single pasteable block — id, level, source, message, stack. `activeErrorLog()` returns the same buffer from anywhere, or `null` if nothing has installed capture yet. Stack frames resolve back to original sources in dev builds, so entries read `board-service.ts:87` instead of `chunk-ab12.js:1:48213`.

<Aside kind="warning">
  <strong>Order matters: <code>startErrorCapture</code> installs the logger sink.</strong>
  Calling <code>setLoggerSink</code> after it replaces that sink, and the buffer silently stops
  receiving <code>logger.warn</code> and <code>logger.error</code> — uncaught throws still land,
  so it looks like it works. Pick one: subscribe to the buffer, or install your own sink and
  forward to it.
</Aside>
