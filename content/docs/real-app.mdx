# A real app: the tracker

The files in `packages/tracker` and `cloudflare/tracker-worker.ts` show these conventions at product size. Read them in the order below.

Run it first:

```
bun run tracker:server   # sync engine on in-memory SQLite — no Docker, no setup
bun run tracker          # vite on :4798
```

Open two browser windows, pick two different users from the bottom-left switcher, and drag a card. Then turn off your wifi and keep working.

The app is called **Axle**. It is a Linear clone: teams, issues, boards, cycles, projects, comments, presence, a notification inbox, full-text search, offline support, and undo for nearly everything. It exists to answer one question — can this framework carry a real product?

<Aside kind="warning">
  These commands start the local Bun demo: in-memory database, trusted user switcher, detailed
  WebSocket errors, and a reset on restart. The branch preview uses a Worker and Durable Object.
  Public production still needs workspace routing, verified identity, backups, restore, and a
  rollout policy. See <code>packages/tracker/ROADMAP.md</code>.
</Aside>

## Read these app files first

| # | File | What it shows |
| --- | --- | --- |
| 1 | `src/sync/issues.sync.ts` | The contract: tables, queries, every mutation with its guess and its `invert` |
| 2 | `src/sync/issues.server.ts` | The truth: the same mutations bound to SQL |
| 3 | `src/services/issue-service.ts` | Where state lives: keyed views, keyed derivations, failed-write toasts |
| 4 | `src/components/list/issue-list.tsx` | A compact connected component with query states |
| 5 | `src/services/issue-interaction-service.ts` | How to get past the three-service connect cap |

**1. `src/sync/issues.sync.ts`.** One file declares the table shape, the queries, and every mutation with its optimistic guess and its `invert`. Read the module comment first: it explains why a new issue's id travels *in the args* (`invert` runs before the optimistic apply, so a create can only name its own inverse if the id already exists) and why the `number` field starts at the sentinel `0` (the `ENG-42` sequence is per-team and only the server can assign it race-free).

**2. `src/sync/issues.server.ts`.** Two things to notice: the create handler computes `max(number) + 1` for the team, which is the field the client deliberately guessed wrong; and `requireActive(tx, issueId)` is a shared guard that throws `rejection('archived', …)`. Business rules live in small reusable helpers, not inline in each handler:

```ts
// Excerpt: packages/tracker/src/sync/issues.server.ts
async function requireActive(tx: ServerTx, issueId: string): Promise<void> {
  const [row] = await tx.sql<{ archivedAt: number | null }>`
    select archived_at as "archivedAt" from issues where id = ${issueId}`;
  if (!row) throw rejection('missing', 'This issue no longer exists.');
  if (row.archivedAt !== null) throw rejection('archived', 'This issue is archived — unarchive it first.');
}
```

**3. `src/services/issue-service.ts`.** This service is the reference for three patterns: `liveQueryFor` creates one subscription per team, lazily on first read; `computedFor` caches one derivation per key; and the private `watch(handle, verb)` helper turns a failed mutation into a toast. That last one is repeated across services and is how a user learns a write did not land:

```ts
// Excerpt: packages/tracker/src/services/issue-service.ts
private watch(handle: MutationHandle, verb: string): MutationHandle {
  void handle.settled.then((info) => {
    if (info.state === 'rejected') this.toastService.flash(`reject:${info.mutationId}`,
      info.rejection?.message ?? `Could not ${verb}.`, 'warn');
    // …'failed' reads info.error?.code; 'orphaned' says someone else deleted it
  });
  return handle;
}
```

**4. `src/components/list/issue-list.tsx`.** This file shows the component contract: `connect()` with a per-instance name, `view()` with named reads, `use:componentRoot` on the real root, and a `<Switch>` over error, loading, empty, and content states.

**5. `src/services/issue-interaction-service.ts`.** Components may reach at most three services. The issue list needs more behavior than that, so this class owns *no* domain logic. It re-exports members of seven bounded services (targets, properties, movement, selection, detail, view navigation, commands). Components keep one stable dependency; each behavior keeps its own file and its own tests. When the lint cap fires, this is the refactor it is asking for.

## Read the Worker and Durable Object runtime

| File | What it shows |
| --- | --- |
| `cloudflare/tracker-worker.ts` | Worker routing, Durable Object boot, WebSocket hibernation, alarms, and readiness |
| `packages/tracker/sync-version.ts` | Application and minimum-client versions shared by all runtimes |
| `packages/tracker/server/schema.ts` | One migration list consumed by Bun and Durable Object runners |
| `cloudflare/tracker.worker.test.ts` | Real Durable Object storage, hibernation restore, and migration failure cases |

The outer Worker serves assets and sends `/sync/*` and `/readyz` to a Durable Object. The object runs `applyDurableObjectMigrations()` before it creates `createCloudflareSyncBackend()`. It accepts sockets through `ctx.acceptWebSocket()`, restores attachments after wake, and runs cycle rollover from a ten-minute alarm.

`packages/tracker/server.ts` remains useful for local development, self-hosting, and runtime parity. Its production-shaped mode proves persistent SQLite, verified sessions, limits, readiness, and graceful shutdown. It is not the default hosted topology.

## Schema, authorization, jobs, search, and tests

| # | File | What it shows |
| --- | --- | --- |
| 6 | `server/schema.ts` | The shared migration list and Bun migration runner |
| 7 | `src/sync/inbox.server.ts` | Authorization on the first read *and* on the live stream |
| 8 | `jobs/rollover.ts` | Writing from outside the engine, safely twice |
| 9 | `src/sync/search.server.ts` | A hand-built query handler: FTS5, bm25, two invalidation channels |
| 10 | `test/m5-fuzz.test.ts` | The adversarial suite: three clients, network chaos, four invariants |

**6. `server/schema.ts`.** Wheel ships no application schema generator, so the app owns one migration list. The Bun runner uses `_axle_schema_migrations` and `begin immediate`. The Durable Object runner consumes the same list through `applyDurableObjectMigrations()`, which owns its bookkeeping format, checksums, and storage transaction. Domain DDL still lives beside its handlers.

**7. `src/sync/inbox.server.ts`.** A query handler receives the caller's `principal`, and the SQL compares the requested `userId` against it. That SQL authorizes the first run and every rerun. Its `prune` callback can skip unrelated work only when a backend supplies row images. The shipped SQLite and Cloudflare backends do not, so they rerun the authorized SQL. Pruning is never a security boundary.

**8. `jobs/rollover.ts`.** The cycle rollover job runs raw SQL directly against the database, then calls `server.externalWrite({ tables: ['cycles', 'issues'] })`. The engine never saw a mutation; it learns which tables changed, re-runs the affected queries, and every subscribed client converges. `now` is a function argument so tests can pass a fixed clock, and ids are derived deterministically with `on conflict do nothing` so a rerun is a no-op. A webhook consumer or a cron worker writes through this same path.

**9. `src/sync/search.server.ts`.** No sugar: a raw `QueryHandler` with SQLite FTS5, bm25 ranking, and *two* invalidation channels — `rerunOn: ['issues', 'comments']` for writes the engine can see, plus a `subscribe` push channel for changes it cannot. Read `toMatchExpr` for how user input becomes a safe MATCH expression.

**10. `test/m5-fuzz.test.ts`.** Seeded weighted operations across three clients with network chaos, then four invariants checked at quiescence: every client holds identical rows, the sync log has no gaps, every write has a known cause, and no optimistic mutation is left pending. The same seed reproduces the same run forever, so a failing seed becomes a permanent fixture.
