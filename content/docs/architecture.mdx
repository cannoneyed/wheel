# Architecture

Wheel's public surfaces stack in one direction, and five locked decisions explain the shape of everything above them.

Wheel is one package with focused subpath surfaces. Each surface imports only from its allowed dependencies. A constraint test and the `no-cross-layer-imports` lint rule fail the build if anyone cheats. The entry-by-entry breakdown is in the [Import Map](#/import-map).

Why this shape:

- **`wheel/auth` and `wheel/config` import nothing internal.** They own trust data and boot-time JSON, so nothing in Wheel has to exist for them to work.
- **`wheel/router` builds on `core` and nothing else.** `RouterService` is a Service like any other, so the URL lands in the same registry as every atom. `wheel/vite` is the same one-edge shape, one layer out: it runs in your build and touches `core` only for the shared clock.
- **`wheel/core` depends only on Solid, Immer, and XState.** Service primitives, the DI container, `connect()`/`view()`/providers, stubs, and registry recording live here. No client, database, or transport enters this layer.
- **`wheel/sync` is renderer-free where it counts.** The `SyncClient` knows nothing about Solid; it exposes plain methods plus one change listener. That is why the whole engine runs headless in tests. `SyncService` and its `liveQuery` views are the thin reactive layer on top, and they depend only on `core`.
- **`wheel/components` is independent.** It ships component families and styles without importing Wheel state layers. `wheel/kit` may compose `components` and `core`, but never `sync`.
- **`wheel/sync/server` is runtime-neutral at its core.** A browser Worker hosts it for local demos, and a Cloudflare Worker hosts it in production. Runtime adapters isolate Bun, Node, WASM, and Durable Object storage so they do not enter the app's main client bundle.

## Locked decisions

Five decisions shape everything else:

1. **Server-authoritative, no CRDTs.** Conflicts resolve by dropping the client's guess and rebasing on server truth. Complexity a small team doesn't need stays out.
2. **Single writer per database.** One writer loop owns every write, behind `SyncBackend.acquireWriterLease()`. SQLite rejects a second in-process engine for the same database identity. A Durable Object already owns one SQLite database.
3. **Whole-row deltas, idempotent by construction.** No patch application logic to get wrong.
4. **Reconnect = fresh bootstrap.** Crash, missed delta, and reconnect are one code path, not three.
5. **Determinism by injection.** Business state receives clock, scheduling, randomness, and ids as injected dependencies. The `no-raw-timers` rule covers every production `src/` file. Native TSX timers are allowed only for presentation timing with an adjacent `wheel-view-timing:` reason.

## The backend interface

The engine is backend-agnostic. The writer loop, subscriptions, presence, row validation, deltas, and replay never touch a database directly. Everything database-shaped lives behind `SyncBackend`. All current implementations use SQLite.

| Backend | Driver | Use it for |
| --- | --- | --- |
| Durable Object SQLite | `ctx.storage.sql` | Production deployment, hibernation, and one database per workspace |
| SQLite in-process | `bun:sqlite`, or `better-sqlite3` under Node and Vitest | Local development, self-hosting, and tests |

## File conventions

A feature's synced data lives in a pair of files: the **sync module** (`todos.sync.ts`) declares tables, queries, and mutations for both sides; the server binding (`todos.server.ts`) attaches SQL and authoritative handlers.
