# Wheel component system audit

This report compares Wheel’s component library with the Astryx catalog. It is also the live tracker for approved component work.

Button and Checkbox define the approved reference format. The catalog now has 156 component pages. Every page uses that format and bundles its behavior spec. Select, Input, Switch, and Avatar are the first current families hardened after those references.

## Main findings

- Wheel has solid primitive depth. All 38 current families have unit tests, and several families expose more parts than their Astryx peers.
- Wheel’s baseline lacks catalog breadth. This branch now gives every missing layout, content, navigation, date, table, feedback, and product-pattern component a public render baseline, spec, and catalog page. Full behavior remains tracked below.
- Most controls have one visual recipe. Shared `sm`, `md`, and `lg` sizes, semantic tones, and density variants do not exist as one typed contract.
- Destructive Alert Dialog styling depends on the demo-only `data-color="red"` convention. The component API does not own that state.
- Catalog demos show one happy path per family. Several fixtures add inline size or label styles, so the recipe is not the full example.
- Unit coverage proves isolated state changes. Browser coverage does not prove most reopen, dismissal, focus restoration, collision, touch, or resize sequences.
- The reported Select failure now has a behavior contract and a repeated-use regression. Pointer and keyboard tests prove three open, select, close, and reopen cycles on one instance.
- Astryx names overlap with Wheel concepts. Adding duplicate engines would weaken composition, so the tracker keeps Wheel names and merges behavior.

## System rules

These rules apply to every current and proposed component.

| Principle | Required behavior | Progress |
| --- | --- | --- |
| Information density | Default controls target compact application layouts. Sizes use a shared scale, with the compact size as the default. | ☑ Defined<br>◐ Implemented (Button, Checkbox, Select, Input, Switch, and Avatar families)<br>◐ Proven (Button, Checkbox, Select, Input, Switch, and Avatar families) |
| Snappy motion | Mounted or opened content appears on the first frame. It does not fade or slide in. | ☑ Defined<br>☑ Implemented (all current recipes)<br>☑ Enforced (Stylelint) |
| Exit motion | Dismissed content may fade or slide out while it remains mounted. Standard fade-out lasts 100 milliseconds. | ☑ Defined<br>☑ Implemented (all current fade recipes)<br>☑ Enforced (motion tokens) |
| State motion | Switch thumbs, progress indicators, drag surfaces, and similar continuous state may move. Their motion does not delay input. | ☑ Defined<br>◐ Implemented (Button, Checkbox, Select, Input, and Switch families)<br>◐ Proven (Button, Checkbox, Select, Input, and Switch families) |
| Composition | Public families expose parts or slots. Consumers can replace content without copying internal state logic. | ☑ Defined<br>◐ Implemented (Button and Checkbox families)<br>◐ Proven (Button and Checkbox families) |
| Modularity | Components do not require an application service. Shared providers cover only cross-cutting concerns such as layers, locale, and theme. | ☑ Defined<br>◐ Implemented (Button and Checkbox families)<br>◐ Proven (Button and Checkbox families) |
| Accessibility | Pointer, keyboard, focus, screen-reader naming, reduced motion, and forced-color behavior are part of the component contract. | ☑ Defined<br>◐ Implemented (Button and Checkbox families)<br>◐ Proven (Button and Checkbox families) |
| Proof | Each required behavior maps to a unit, browser, accessibility, or visual assertion. A demo is not proof. | ☑ Defined<br>◐ Implemented (Button and Checkbox families)<br>◐ Proven (Button and Checkbox families) |

The motion rule is system-wide. Component recipes may style `[data-ending-style]` for 100-millisecond exit motion. Stylelint rejects every `[data-starting-style]` selector and every raw timing literal in Wheel component CSS, so new entry motion or private timing fails `bun run lint`.

## Spec contract

Specs live beside their component source:

```text
packages/wheel/src/components/<family>/<component>.spec.md
```

Each public Wheel catalog entry gets one spec. Namespace parts such as `Dialog.Popup` stay in `dialog.spec.md` unless Wheel exports them as standalone catalog entries.

Each spec uses bullet points under these headings:

- Purpose and when to use the component.
- Public parts, slots, and valid compositions.
- Visual sizes, tones, density, orientation, and layout variants.
- Controlled and uncontrolled state.
- Pointer, touch, keyboard, and focus behavior.
- Labels, roles, announcements, and error semantics.
- Disabled, loading, empty, invalid, read-only, and overflow states.
- Open, close, dismissal, collision, portal, and scroll behavior when relevant.
- Immediate entry, exit-only motion, and reduced-motion behavior.
- Responsive, right-to-left, high-contrast, and zoom behavior.
- Required unit, browser, accessibility, and visual proof.

The Select spec must include this sequence as one browser assertion:

1. Open the Select.
2. Choose an item.
3. Confirm that it closes and shows the chosen value.
4. Open the same Select again.
5. Choose a different item with pointer input.
6. Repeat the sequence with the keyboard.

Wheel’s Select unit and browser tests now run this full sequence. The browser test mixes pointer and keyboard input across three selections to prevent the reported reopen failure from returning.
